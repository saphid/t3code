**One note, not blocking and not caused by this diff**

The page script only posts `connecting` when the socket drops after the first frame has been painted. The check is `if (streaming) reportStatus("connecting")` in `apps/mobile/src/features/browser/preview-stream.browser.ts:233`. If a connection delivers a control message carrying a dialog and then drops before its first frame, neither the ref nor the existing `setControl(null)` gets cleared.

For this to keep a stale draft, all of these would have to happen:
1. The disconnect lands in the gap between the control message and the first frame.
2. The user types into the prompt during that gap.
3. An identical dialog closes and reopens while the socket is down.

That chain is extremely unlikely. The gap itself predates this change, and it affects control state generally, not just the draft. Closing it would mean posting `connecting` on every disconnect, which is out of scope for H-2.
