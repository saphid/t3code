# Customization surface inventory

Date: 2026-09-22

The current product already personalizes appearance, shortcuts, thread organization, and pane
dimensions. The missing layer is selective visibility and ordering inside the high-frequency UI:
thread rows, the composer, and the workspace panel. Those controls should be small, reversible,
and stored as client preferences with safe defaults. A plugin should be able to add a new panel
section or composer action through an explicit extension point, but should not rewrite core row
semantics or silently change a user's built-in defaults.

Desktop loads the web bundle, so the web controls above are the main desktop experience; its native
shell separately persists window bounds and maximized state ([DesktopAppSettings.ts:27](/Users/aus-m5p-as/projects/t3code-contrib/apps/desktop/src/settings/DesktopAppSettings.ts:27)) and writes the same client settings schema ([DesktopClientSettings.ts:1](/Users/aus-m5p-as/projects/t3code-contrib/apps/desktop/src/settings/DesktopClientSettings.ts:1)). Mobile uses the shared runtime with a separate native layout ([workspace-layout.md:13](/Users/aus-m5p-as/projects/t3code-contrib/docs/internals/workspace-layout.md:13)), so preference names can be shared while controls remain platform-specific.

## Built-in personalization versus plugins

Built-in personalization belongs in `ClientSettingsPatch`, whose current schema already covers
appearance, typography, browser defaults, sidebar behavior, and model preferences
([settings.ts:863](/Users/aus-m5p-as/projects/t3code-contrib/packages/contracts/src/settings.ts:863)). These values are bounded, resettable,
and shared between web and desktop. Mobile also has its own appearance persistence. New row, panel,
and composer preferences should use shared meanings with explicit adoption in each client rather
than assuming a schema change implements mobile behavior. Layout state such as sidebar width can stay in
client storage as the existing implementation does.

Plugins should contribute named capabilities, not arbitrary layout mutations. A panel plugin can
register a section and its `When relevant` predicate. A theme extension can contribute validated
color data. A composer plugin can contribute a command or context provider. Core code should own
ordering, visibility state, accessibility labels, reset behavior, and failure handling. That keeps
the no-setup path coherent and makes every extension removable without corrupting the built-in UI.

The strongest first slice is the proposed floating panel customization plus thread-row presets.
They affect repeated daily decisions, have obvious defaults, and can be implemented as reversible
client preferences. Composer control visibility follows next, with mobile parity designed at the
same time. Appearance and shortcuts already provide the interaction patterns to copy.
