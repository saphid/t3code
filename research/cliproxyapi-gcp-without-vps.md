# CLIProxyAPI on GCP without a dedicated VPS

_Researched 8 September 2026. Sources are limited to the official CLIProxyAPI repositories and Google Cloud documentation._

## Recommendation

Yes. The nicest current option is a **single Cloud Run instance**, using CLIProxyAPI's native S3-compatible object-store backend with a regional Cloud Storage bucket. This is a newly released **Preview** resource, distinct from an ordinary Cloud Run service. It runs exactly one continuously addressable container, has a stable HTTPS URL, does not autoscale, and restarts automatically after its roughly seven-day runtime lifecycle. Google positions it specifically as a lightweight serverless VM for personal agents and quotes **$5.70 for 1 vCPU and 1 GiB running for 30 days** in its launch example. ([Cloud Run instance overview](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [launch announcement](https://cloud.google.com/blog/products/serverless/introducing-cloud-run-instances))

This should first be treated as a small pilot because the resource is Pre-GA and because CLIProxyAPI documents generic S3 compatibility, not Cloud Storage specifically. Keep the current small Compute Engine gateway until the four validation gates below pass. If Preview infrastructure is unacceptable, the small VM remains the simplest production choice. GKE Autopilot is sensible only if a cluster already exists.

## Why state changes the answer

CLIProxyAPI is not stateless. Provider OAuth tokens are JSON files under `auth-dir`, and refreshed credentials are written back through its token store. Its official Docker example mounts both `config.yaml` and the auth directory. ([auth-dir documentation](https://github.com/router-for-me/CLIProxyAPIDocs/blob/e5893d0dbcb2af29d8dd4a17f8b6d6996f950ee4/docs/en/configuration/auth-dir.md), [Docker quick start](https://github.com/router-for-me/CLIProxyAPIDocs/blob/e5893d0dbcb2af29d8dd4a17f8b6d6996f950ee4/docs/en/introduction/quick-start.md), [refresh persistence](https://github.com/router-for-me/CLIProxyAPI/blob/d198db54d4c4886c99b21488d54fc576933019a3/sdk/cliproxy/auth/conductor_lifecycle.go#L408-L430))

Upstream already provides the right abstraction for disposable containers: `OBJECTSTORE_*` settings bootstrap config and auth files into a local mirror, then upload mutations to an S3-compatible bucket. The implementation uses a MinIO client with V4 signatures and path-style requests, writes auth locally with temp-file-plus-rename, and uploads on save. ([object-store configuration](https://github.com/router-for-me/CLIProxyAPIDocs/blob/e5893d0dbcb2af29d8dd4a17f8b6d6996f950ee4/docs/en/configuration/storage/s3.md), [server wiring](https://github.com/router-for-me/CLIProxyAPI/blob/d198db54d4c4886c99b21488d54fc576933019a3/cmd/server/main.go#L247-L263), [object-store implementation](https://github.com/router-for-me/CLIProxyAPI/blob/d198db54d4c4886c99b21488d54fc576933019a3/internal/store/objectstore.go#L141-L233))

Cloud Storage's XML API supports S3-style tooling, HMAC-SHA256 credentials, and the path-style `https://storage.googleapis.com/BUCKET/OBJECT` endpoint. That matches upstream's client shape. However, the credentials are a static HMAC access ID and secret, not Application Default Credentials, so they must be held in Secret Manager and rotated. Google also documents a few XML API differences from S3, so this exact MinIO/GCS pairing needs a smoke test. ([XML API interoperability](https://docs.cloud.google.com/storage/docs/xml-api/overview), [path-style endpoint](https://docs.cloud.google.com/storage/docs/request-endpoints), [HMAC keys](https://docs.cloud.google.com/storage/docs/authentication/hmackeys), [S3 migration differences](https://docs.cloud.google.com/storage/docs/migrating))

The store's locking is process-local and startup performs a one-way bucket-to-local sync. There is no cross-instance compare-and-swap. Therefore, **run exactly one writer**. Multiple Cloud Run service revisions or replicas could overwrite a newer refresh with stale local state. This is an inference from the upstream implementation. ([store mutex and bootstrap](https://github.com/router-for-me/CLIProxyAPI/blob/d198db54d4c4886c99b21488d54fc576933019a3/internal/store/objectstore.go#L45-L59), [upload path](https://github.com/router-for-me/CLIProxyAPI/blob/d198db54d4c4886c99b21488d54fc576933019a3/internal/store/objectstore.go#L483-L499))

## Proposed shape

1. Run the official CLIProxyAPI container as one Cloud Run instance in Sydney, listening on its configured application port, with restart policy `always`.
2. Use a pre-created regional Cloud Storage bucket through `OBJECTSTORE_ENDPOINT=https://storage.googleapis.com`, bucket name, HMAC access ID/secret, and a local mirror under disposable storage. Keep config and all provider OAuth JSON in that backend.
3. Assign a dedicated Cloud Run service account. Use it for Secret Manager and other Google APIs without a service-account key. Its identity can also be the basis of the existing Vault GCP-auth exchange, subject to the current Vault role accepting the new principal. ([Cloud Run instance service identity](https://docs.cloud.google.com/run/docs/configuring/instances/service-identity), [instance secrets](https://docs.cloud.google.com/run/docs/configuring/instances/secrets))
4. Restrict ingress to `internal` if only same-project VMs and approved internal systems call the proxy. Cloud Run still uses the stable `run.app` HTTPS URL, with IAM authentication as an additional layer if clients can supply Google identity tokens. Same-project VPC traffic qualifies as internal. ([Cloud Run ingress](https://docs.cloud.google.com/run/docs/securing/ingress))
5. Keep CLIProxyAPI's own API key enabled. If existing clients cannot attach Cloud Run IAM tokens, use internal ingress plus the application key, or put an internal Application Load Balancer in front. Do not make the unauthenticated management API public.
6. Run the AI Enablers Vault refresh loop continuously in the same instance, either as a small sidecar or supervised companion process. Write short-lived Vault material only to shared ephemeral storage or memory. Let CLIProxyAPI's watcher reload the generated config. Do not rely on request traffic to wake the refresh loop.

## Go/no-go tests before cutover

1. **Object compatibility:** pre-create the bucket, boot against `storage.googleapis.com`, refresh each provider once, restart the instance, and prove every updated OAuth JSON is restored. Also test config mutation and deletion.
2. **Singleton safety:** confirm deployments and updates never overlap two writers. Cloud Run instances promise one runtime, but an update's exact handover behavior should be observed.
3. **Long streaming:** hold an SSE response beyond 60 minutes. Google's quota table associates the 60-minute cap with services, not the new instance resource, but the Preview path needs an end-to-end proof. ([Cloud Run quotas](https://docs.cloud.google.com/run/quotas))
4. **Refresh continuity:** prove provider OAuth refresh and the Vault-backed AI Enablers refresh both continue with no incoming requests, then survive the platform's scheduled restart. Cloud Run instances run up to seven days per execution and restart according to policy. ([instance lifecycle](https://docs.cloud.google.com/run/docs/instances/instance-lifecycle))
5. **Private reachability:** call the internal endpoint from the actual build VM or T3 environment, including a VM with no external IP. Google notes that Private Google Access or an appropriate private networking path may be needed for such callers. ([private Cloud Run networking](https://docs.cloud.google.com/run/docs/securing/private-networking))

If all five pass, Cloud Run instance plus the native object-store backend removes the proxy VM cleanly. If any fail, retain the e2-small gateway rather than layering Filestore, GKE, or custom synchronization around an ordinary Cloud Run service.
