# OV2 provider session recovery audit

Audit target: shipped OV2 source at `/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source`, commit `fe37370dfbd4ff870a81a9393e39ab90948555d6`.

## Conclusion

OV2 separates durable conversation and provider-thread records from live provider runtime residency. `ProviderSessionManagerV2` owns live sessions, idle release, explicit shutdown, and release after runtime failure. Its own contract says it does not resurrect persisted sessions; process-loss recovery terminalizes provider-bound work and a later command opens a session lazily ([ProviderSessionManager.ts:62](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderSessionManager.ts:62)). Therefore a restart can resume a saved provider conversation when the provider has a durable native session id, but it cannot reattach an already-running shell, tool call, approval request, or provider process.

The shipped user-facing switch is **Settings → General → Continue threads after restarts**. It is off by default, survives in connected environment settings, and only resumes supported active threads. Terminal commands can still be interrupted, and threads without saved provider resume state need a new message ([docs/user/updating.md:8](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/docs/user/updating.md:8)).

## What startup and shutdown do

At startup, `ProviderRuntimeRecoveryService` identifies nonterminal runs, expires pending non-message runtime requests as `not_resumable`, cancels stale runs and their pending provider turns, clears active provider-thread/background-task state, and marks live provider-session projections stopped ([ProviderRuntimeRecoveryService.ts:139](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts:139), [ProviderRuntimeRecoveryService.ts:219](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts:219), [ProviderRuntimeRecoveryService.ts:442](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts:442)). Queued runs are held for explicit consent rather than silently drained ([ProviderRuntimeRecoveryService.ts:205](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts:205)).

If continuation is enabled, startup schedules a continuation only when the latest run is eligible. Eligibility requires an unarchived, undeleted thread, the same provider instance, a strong native thread id, a matching live session record, and a running provider turn ([RestartContinuation.ts:15](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/RestartContinuation.ts:15)). The continuation dispatches the stable message **"Continue where you left off."**, deduplicates by deterministic message id, and gives any newer user run precedence ([RestartContinuation.ts:70](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/RestartContinuation.ts:70)). This is a new provider turn on the old native conversation, not a reattachment to the interrupted turn.

Shutdown interrupts the effect worker, persists continuation intent when enabled, closes all live provider sessions, and runs shutdown reconciliation ([serverRuntimeStartup.ts:429](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/serverRuntimeStartup.ts:429)). Session release closes the adapter scope, ends or closes subscribers, persists a stopped session record, and resolves live runtime requests as cancelled/not resumable; scope close is time-boxed to 30 seconds ([ProviderSessionManager.ts:699](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderSessionManager.ts:699), [ProviderSessionManager.ts:1511](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderSessionManager.ts:1511)).

## Practical recommendation

Alex narrowed the scope after this audit. Use the existing **Continue threads after restarts** setting for best-effort recovery. Do not add a recovery dashboard or a separate process manager.

The local environment's setting was enabled through the normal authenticated settings API and read back as `true`. No project overrides disable it. The temporary API session was revoked afterward. Evidence is in [ov2-restart-continuation-enabled-20260918.json](ov2-restart-continuation-enabled-20260918.json). No build or restart was needed to enable it.

The only optional follow-up is **Install when active work finishes**. Keep it a per-update choice with a visible pending state and **Cancel**. Waiting for user approval still counts as unfinished work. A scheduled install must recheck activity before restarting, and must not treat a disconnected environment as idle. This option has not been implemented or added to the prepared release.

If the requirement is specifically that shell commands, tool calls, approvals, or provider processes continue through a server upgrade, that is a separate worker-supervisor problem. It would require a durable process owner and reconnect protocol per provider, plus recovery of callback capabilities. OV2 resolves live runtime requests as cancelled or expired with a `not_resumable` capability during process-loss reconciliation ([ProviderRuntimeRecoveryService.ts:172](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts:172), [ProviderSessionManager.ts:605](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/ProviderSessionManager.ts:605)). A separate supervisor should be considered only if ongoing execution across server upgrades is a hard requirement.

No end-to-end provider restart test was run in this audit. The subsequent scope decision enabled only the existing environment preference through its normal API. Product files and running processes were unchanged.

## Desktop restart versus server restart

Alex's Mac already has a separate launchd server configured in `~/Library/LaunchAgents/com.t3tools.t3code.service.plist`, with `KeepAlive` and `RunAtLoad` enabled. This was inspected read-only. A desktop-only restart can therefore leave that independently managed server and its agents running. This is different from a desktop-owned bundled backend: the desktop stops its owned backend pool on quit and before installing a desktop update ([DesktopApp.ts](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/desktop/src/app/DesktopApp.ts:147), [DesktopUpdates.ts](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/desktop/src/updates/DesktopUpdates.ts:753)). A server update or machine reboot still requires recovery after the server starts again.

The setting is under **Settings > General > Continue threads after restarts**. It is now enabled on the local environment; other environments retain their own preferences. If an intended environment was offline, use **Apply to all** after it reconnects. The first Alpha-to-Fork migration still requires finishing or stopping active turns. Its installer explicitly refuses an active-turn count above zero ([install.py](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/install.py:106)).

## Persistence and verification boundary

OV2 writes events, derived state, and pending effects in a shared transaction, then publishes the committed events to clients ([EventSink.ts](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/EventSink.ts:323)). Saved conversation state is durable. Any output that had not reached persistence at the instant of a crash is outside that guarantee.

Existing tests cover another crash before the resumed provider starts, deduplicated continuation dispatch, newer user work taking precedence, and a run completing while shutdown intent is saved ([RestartContinuation.test.ts](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/RestartContinuation.test.ts:124), [FoundationPersistence.test.ts](/Users/aus-m5p-as/.local/share/t3-ov2-builds/20260918-hosted-final/source/apps/server/src/orchestration-v2/FoundationPersistence.test.ts:2530)). These tests were inspected, not rerun during this audit. Stable continuation IDs avoid submitting the recovery message twice; they do not guarantee that an external action cannot be repeated if its outcome was unknown at the time of a crash.

Before treating active execution as seamless, exercise isolated real-provider cases: desktop reconnect with the service kept alive, graceful server restart mid-turn, crash mid-turn, pending approval, held queue, and a second crash during recovery. Verify restored conversation identity, one continuation submission, accurate terminal states, and explicit reporting when recovery cannot proceed.
