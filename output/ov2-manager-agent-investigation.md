# Cheap manager agents for Orchestrator V2

Research date: 18 September 2026, Australia/Sydney. Requested by Alex as a new ordinary research/design thread, originating in `19f76675-d149-47f5-ba43-9f7a9fb86966`. This report is the complete deliverable. No product implementation, PR, settings change, browser session, or child agent was started.

**Recommendation: add an optional managed delegation mode to V2, using an app-owned manager thread and deterministic server supervision.** Use a cheap model for dispatch and bounded decisions. Keep the capable planner asleep until the batch finishes, its budget is exhausted, or a decision exceeds the manager's mandate. Do not insert a manager into every task.

The hierarchy is partly feasible today. V2 already supports nested app-owned tasks, direct-parent completion delivery, durable completion ownership, and recovery. It also distinguishes a finished manager turn from finished managed work. The missing pieces are a durable batch lifetime, campaign-wide budgets and action limits, reliable delivery beyond the existing two-wake allowance, and explicit escalation and cancellation semantics. Prompting alone cannot guarantee those properties.

The historical evidence supports Alex's workflow, but does not establish that every part was delegated in one successful campaign. The strongest local example is a Fable planner handing prewritten prompts to a GLM manager that launched, supervised, nudged, and resumed workers. Fable still performed review acceptance and several repair decisions. A separate earlier workflow shows a manager creating review threads, including a concrete lifecycle failure. Neither the consistency poller nor the large migration-monitor transcript is proof of the whole hierarchy.

**Three choices**

| Choice                                      | Benefit                                                                                                                                                      | Cost and failure boundary                                                                                                                                                            | Judgment                                                                                                                        |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Prompt-only planner to manager to workers   | Available now with explicit cheap target and app-owned delegation. Can dispatch reviewers using `role=review`, retrieve results, and send follow-up prompts. | Relies on instructions for budgets, persistent intent, repair choices, and future work. Two-wake cap, native restrictions, cancellation gaps, and session-scoped idempotency remain. | Suitable for short, supervised batches. Not sufficient for a reliable unattended manager.                                       |
| Optional first-class managed delegation     | Reuses V2 children and mailboxes while adding durable batch state, bounded actions, event-based wakes, and explicit escalation.                              | Moderate backend work plus client controls and focused lifecycle tests. Needs deliberate recovery behavior.                                                                          | Smallest useful product implementation.                                                                                         |
| Always-on or automatically inserted manager | Could supervise all work through a common policy.                                                                                                            | Adds a model turn and another source of mistakes to trivial tasks, increases latency and context, and complicates every provider path.                                               | Not justified by the evidence. Always-on deterministic observation can be cheap; always-on model reasoning is a different cost. |

A prompt-only trial should explicitly request an app-owned cheap manager, pass a compact manifest of worker and review prompts, retain task IDs, and treat review acceptance as evidence rather than model prose. It can demonstrate the user experience. It should not be advertised as durable unattended operation. Keeping a model in a sleep/poll loop just to avoid lifecycle gaps defeats much of the intended saving.

The recommended flow is:

```text
Alex can inspect, pause, override, or cancel at any time
                         |
Capable planner writes the batch brief, prompts, and limits
                         |
                  Planner goes idle
                         |
Server stores batch state and watches task events and deadlines
     |                   |
     | routine facts     | a bounded decision is needed
     | no model call     v
     |              Cheap manager turn
     |                   |
     +------ launches workers and independent reviewers
                         |
                Results return to manager
                         |
          Server checks receipts, limits, and next action
                         |
      Planner wakes only for batch done, exhausted budget,
                 or a decision outside the brief
```

**Proposed managed-batch contract, not current behavior**

Use an optional `management` object on `delegate_task`, rather than a new general workflow language. It creates one manager task and a durable batch record. The planner supplies an explicit manager target, allowed worker/reviewer targets, immutable prompt references or stored prompt text, acceptance checks, dependencies, workspace ownership, and limits. Ordinary delegation keeps its present semantics.

The record needs a batch ID, planner thread and originating run, manager thread, owner generation, plan revision, task slots, attempt IDs, review round, result references, last processed event sequence, pending decision, action receipts, and remaining budget. A task slot is the intended unit of work; replacing a provider thread creates another attempt in the same slot. Suggested batch states are `running`, `waiting`, `needs_decision`, `budget_exhausted`, `completed`, `paused`, and `cancelled`. An idle manager turn does not change the batch to completed.

1. The server consumes task/run/provider/request events and keeps a small durable inbox. It batches related terminal events and allows one manager decision turn at a time. No model wake for unchanged status, elapsed polling intervals, or heartbeat bookkeeping. Dependency transitions, schema checks, counters, and known backoff rules are deterministic.
2. A manager turn receives the plan summary, remaining limits, state changes since its acknowledged event sequence, result references, and one pending decision. It can dispatch an allowed slot, start its designated reviewer, forward concrete review findings, request one bounded retry, wait, finish, or escalate. It cannot expand the task set, change acceptance criteria, silently choose a costly model, or reset counters.
3. Action identity is `{batchId, planRevision, slotId, attempt, actionKind}` and survives provider-session changes. The server records intent before effects and receipts afterward. On uncertainty, reconcile the existing command, thread, and attempt before creating anything new. Repeated or stale manager responses are safe no-ops or explicit rejections. Do not claim exactly-once filesystem execution.
4. Review output includes the reviewed commit or artifact digest, findings, severity, and verdict. The manager can route a declared fix round; acceptance requires the specified checks and correct artifact identity. Cross-vendor review follows model routing. Cheap management does not imply cheap final review. New architecture, ambiguous requirements, irreconcilable reviews, or changed acceptance criteria escalate.
5. Emit one planner message per escalation generation with reason `batch_complete`, `budget_exhausted`, or `decision_required`. Include completed and blocked slots, evidence references, actions already tried, actual and estimated usage, options, a recommendation, and the exact answer needed. Deduplicate it until the planner or Alex responds. Routine child completion never becomes a planner notification.
6. `batch_complete` requires every required slot accepted or explicitly waived, no active attempts or unresolved mandatory review, and a final compact report. `decision_required` pauses the affected branch, or the whole batch when unsafe to proceed. An exhausted budget stops new paid decisions and new workers; deterministic status recording continues. Do not wake the expensive planner repeatedly when its own budget is exhausted; record the escalation visibly and wait for user authorization if no planner allowance remains.
7. Default to one manager level and leaf workers/reviewers with recursive spawning disabled. Enforce one shared descendant budget at the batch root across replacements and reviews. Initial defaults can follow the local policy's eight concurrent children, thirty-two total children, and $250 API-equivalent child-cost approval ceiling, but resolve effective limits against stricter configured project/thread thresholds. Count manager turns, reviewers, context, time, and launch reservations too. Warn at 80 percent. Do not let a new manager session reset usage.
8. Stop and cancel are durable actions. Pause prevents launches and model wakes while retaining work; resume is explicit. Cancel revokes future actions, walks all owned attempts, requests interrupts, and records any child that could not be stopped. A planner merely ending a turn is not cancellation. Archive/delete and explicit Stop must have visible, defined effects on the batch instead of silently abandoning it.

A failed turn, a slow tool, a rate-limited provider, an unanswered approval, and an idle worker are different states. Observe pending requests and provider retry state before considering restart. Quiet time is evidence to inspect, never proof of failure. A known transient failure may get one resume on the same attempt under a defined backoff. A replacement requires terminal confirmation or isolation from the old attempt. If stop confirmation is unavailable, pause and escalate instead of starting a competing writer. Native work whose liveness cannot be reconstructed is `unknown`, not automatically dead.

The first version should make stale-work detection advisory. Permit automatic recovery only for narrowly classified failures whose old attempt is known stopped. This is smaller and safer than implementing bucket-2's full heartbeat-based restart scheme. A new worktree per writing attempt, or serialized ownership of shared files, is the real protection against overlapping writes. A lease field enforced only by a prompt is not sufficient.

Permission policy needs care. Current MCP forbids a narrow manager runtime from launching broader workers. Preserve that rule for the first version. Require an explicitly authorized execution-capable parent and inherit its ceiling; constrain manager actions through server-validated managed commands and provider tool restrictions where supported. If a future design wants a read-only manager to dispatch preauthorized writing workers, represent that authority separately in the batch contract. Do not silently weaken `resolveRuntimeMode`. Approval requests remain for the user, and a manager must not auto-answer them just to make progress.

A prompt-only demonstration is roughly 0.5 to 1 unit. A narrow optional manager implementation is roughly two to four engineering weeks, depending on existing usage-accounting reuse and cancellation work. Full native-child management and cross-environment execution are separate expansions, plausibly larger than the initial feature. Always inserting a manager expands the compatibility and performance burden and has no evidence-backed payoff here.

The client scope applies to chat and the Agents view on web, desktop, and mobile. Any command-palette or keybinding entry must invoke the same pause/cancel commands. Settings only need defaults if product demand warrants them; an explicit per-delegation option is enough initially. Provider-specific capability reporting is required. Local, relay, and tunnel clients should use the same server-owned batch, and concurrent clients must see the same override generation. Cross-environment scheduling, automatic PR publication, a generic workflow editor, and manager-created policy changes are outside the smallest implementation.

**Failure and cost analysis**

| Failure or cost                 | Why it matters                                                                                                                                            | Required control                                                                                                                                                     |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unnecessary model wakes         | A cheap model that repeatedly reads a large transcript can cost more than a small deterministic check. An extra manager also adds latency to simple work. | No model calls for ordinary monitoring. Batch events and call only for decisions. Measure planner wakes avoided and total campaign cost.                             |
| Context growth                  | Long polling campaigns accumulate duplicated instructions and stale facts. The Phase 3.1 history is a concrete warning about size.                        | Durable task state, bounded evidence excerpts, event cursors, and compact handoffs. Keep raw worker logs outside manager prompts.                                    |
| Manager misclassification       | Bucket-2 misread a template heading as a blocker and needed revised stale-work rules.                                                                     | Typed outcomes and pending-request state. Treat unsupported inference as a decision needing evidence, not an automatic restart.                                      |
| Duplicate execution             | Delivery is at least once; session-scoped request IDs and uncertain tool results can produce duplicate attempts.                                          | Durable action keys, receipt reconciliation, attempt ownership, and no replacement until old work is stopped or isolated.                                            |
| Infinite review/restart loops   | "Keep going until green" has no natural bound. More turns can recycle the same failed solution.                                                           | Two full review rounds by default, bounded delta follow-up, per-slot replacement cap, total launches and cost/time limits. Escalate repeated failure or no progress. |
| Shared-worktree conflicts       | The manager can schedule disjoint-looking tasks that modify common lockfiles, generated files, or evidence.                                               | Explicit ownership, separate worktrees for writes, serialized integration, and artifact digests. | Manager as single failure point | Workers can finish while the cheap model is unavailable or confused.                                                                                      | Server owns state and inbox. Retry a bounded decision, retain results, then expose a paused batch. Alex or a new manager can take over with a new generation.        |
| Lost work after restart         | A restored thread does not restore external processes, pending approvals, or uncommitted tool effects.                                                    | Reconcile receipts and actual provider state; preserve result artifacts; mark uncertain attempts and expired approvals explicitly. Resume from a compact manifest.   |
| Masking hard problems           | A cheap manager may invent acceptance, weaken a task, or endlessly nudge when design work is needed.                                                      | Immutable acceptance criteria, reviewed artifact identity, typed decision reasons, and explicit authority limits. Route hard judgment to the planner.                |
| Permission bypass               | A manager can mistake an approval wait for a stall or treat a replacement as fresh authorization.                                                         | Preserve runtime ceilings and pending approvals. Replacement retains the same authorization boundary.                                                                |
| Invisible cancellation failure  | Stopping a manager's turn does not necessarily stop its native or app-owned descendants.                                                                  | Batch-level cancellation receipts, descendant inventory, and visible "stop incomplete" status. No successful-cancel label until accounted for.                       |
| Hidden budget overrun           | Billing data can lag or lack accurate pricing for custom providers.                                                                                       | Reserve conservative limits before dispatch, label estimates, apply token/turn/runtime caps when dollar precision is unavailable. Never treat unknown cost as zero.  |

The economic comparison is `saved planner follow-up cost > manager decision cost + extra review/retry cost + operational overhead`. For illustration only, twelve planner follow-ups reduced to one batch report and one escalation avoid ten planner turns. Ten manager turns and their context must cost less than those ten avoided turns, including any extra retries they cause. No measured savings or vendor-price claim is made here. Track input/output/cache tokens, cash versus API-equivalent cost, decision latency, escalation rate, false restarts, and duplicate actions before broadening the feature.

**Validation and remaining evidence gaps**

I inspected source and tests without installing dependencies, running providers, or executing a test suite. Existing tests cover nested-work gating, batching without implicit acknowledgement, live-cohort text/metadata, idempotent acknowledgement/disposal, message-text versus buffered wake delivery, transient retries, archive/delete drops, and stale-generation suppression. They support the code reading; they are not a fresh passing-test claim. Useful entry points are [SubagentProjection.test.ts][progresstest], [DelegatedCompletionDelivery.test.ts][deliverytests], [ProviderContinuationService.test.ts][continuationtests], and the native-adapter tests cited above.

Before implementing, pin the intended release base and add focused receipt-driven tests for these cases:

1. Planner delegates manager; manager delegates three workers; their completions do not wake the planner. Manager ends a turn with workers active and remains incomplete.
2. Three staggered completions exceed the generic two-delivery cohort allowance. Managed mode consumes every result without a polling model or silent pending tail.
3. Restart at each boundary: action intent, worker creation, result persistence, offer, provider acceptance, acknowledgement, and escalation. Replays do not duplicate a worker, review, or planner wake.
4. Approval wait, long-running tool, rate limit, failed provider, and unresponsive process produce distinct decisions. No replacement races a still-writing worker.
5. Manager model failure, user override, parent ordinary completion, explicit Stop, archive/delete, and recursive batch cancellation have explicit outcomes.
6. Budget exhaustion, recursion attempts, costly-target substitution, stale review digest, and repeated review findings are rejected or escalated deterministically.
7. Web/desktop/mobile render the same batch and support pause, resume, inspect, and cancel over local and remote connections. Native children expose only controls the adapter can actually honor.

Evidence gaps remain bounded and explicit. I did not locate one cheap-manager campaign proving independent review creation, routine review repair, and complete planner sleep all together. Bucket-2 strongly proves dispatch/supervision and durable handoff, but retained expensive acceptance work. The earlier review-manager workflow proves review dispatch and a lifecycle failure, with unknown manager model. Its historical workflow script path is now missing. No remote machine was queried, and references to earlier Ben workstreams were not expanded into another campaign search. The origin thread UUID is taken from Alex's request; it was not present in the legacy projected thread lookup. Installed-build provenance was verified, but live runtime behavior and exact cost savings were not measured.

The current foundation is enough to avoid inventing a second orchestrator. The smallest useful change is an opt-in durable managed batch around existing app-owned tasks, with server-enforced limits and explicit final/escalation delivery. The model should decide only what deterministic state and declared policy cannot decide.
