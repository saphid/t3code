The main fix is otherwise correct: text typed during the save, removals of existing attachments, and draft attachment or context changes are all kept, and saving is released in the `finally` block on every path. This was a code reading only; I did not run the tests.

**Medium: `apps/mobile/src/state/use-thread-composer-state.ts:552`.** The check that decides whether the composer stays in edit mode compares the attachments list by object identity (`currentDraft.attachments !== draft.attachments`). A background upload can replace that list during a save even when the user changed nothing, so a successful save can wrongly leave edit mode open.

- **Why the list gets replaced:** the background upload worker, `useComposerAttachmentUploadWorker` (`apps/mobile/src/state/composer-attachment-uploads.ts:57-140`, mounted in `Stack.tsx:616`), uploads attachments from every draft. That includes the queued-edit draft, because `composerDraftEnvironmentId` reads the environment from the `env:thread~queued-edit~run` key. When an upload finishes, `setComposerDraftAttachmentUpload` (`apps/mobile/src/state/use-composer-drafts.ts:1470-1500`) writes back the upload id by rebuilding the list, giving it a new identity even though the user's content is the same. The save itself doesn't wait for this upload: it runs its own `prepareTurnAttachments` and never checks the upload block reason.
- **How to hit it:** start editing a queued message, add an image or file, and tap Save before the background upload finishes. This is likely on slow remote or T3 Connect links. The upload finishes while the save is preparing or waiting on the RPC, and the RPC succeeds. The identity check then fails, so the edit is never ended.
- **What the user sees:** the save went through, but the composer stays in edit mode showing content the server already has. They have to Save again, which repeats the edit request. If the run starts first, the effect at `use-thread-composer-state.ts:449-465` copies the already-saved text into the thread's own draft and shows "That message already started. Your edit is back in the composer." That message is wrong here, because the edit was in fact saved. On base, a successful save always closed edit mode, so this is new behaviour.
- **Why the tests miss it:** they mock the upload worker away and only change attachments by adding a new item.
- **Suggested fix:** compare by content, not by object. For example, check that the attachment id lists are the same length and match in order, ignoring `uploadedAttachmentId`/`uploadEnvironmentId`. Keep the identity check for `context`, which uploads never touch.
